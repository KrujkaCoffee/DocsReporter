# Этап 8.1А — проверяемый просмотр изделия

## Граница этого выпуска

Отдельный экран `/reporter/product.html`: найти карточку, получить назначенное изделие,
раскрыть состав по одному уровню и увидеть собственные папки PDF/DXF/CAD выбранного элемента.
Это промежуточная реализация для проверки данных, НЕ готовый промышленный выпуск.

Обработка данных построена на текущем GitHub-снимке:
- Репозиторий: `KrujkaCoffee/DocsReporter`.
- Базовый коммит: `9c67dc7899bc83166193a19b1a9daf9e72e2249c`.
- Проверенное дерево: `e14a58328b78c214a6747d5d669e516505b1ba76`.
- Содержимое локальной исходной копии проверено `git write-tree`; дерево полностью совпало с GitHub.
- Изменения в GitHub не отправлялись. Архив и patch являются результатом этой итерации.

Существующие контроллеры карточек, справочников, диагностики и старый `FileController` сохранены.
Добавлена одна ссылка «Изделие» в старом главном интерфейсе. Старый экран не использован как
источник данных нового: новый экран НЕ вызывает старый full-card и НЕ смешивает ТЗ/ВО с РКД.

## Подтверждённое происхождение данных

Пользователь отдельно подтвердил: последние семь CSV от 12.10.2026 выполнены в
`SRV-TDOCS / TFlexDOCsOne`, ключ репортера — `tdocs`.
Первый CSV `01. Источник` с `master` не используется как происхождение остальных семи.
`report_sql.md` используется для формы запросов того же примера.
Старые SQL-дампы проекта НЕ импортировались и НЕ использовались как данные `tdocs`.
Предположение, что все они принадлежат PKB, не превращено в установленный факт.

В runtime нет общей константы `ProjectCardGroupId = 891`, а число 891 в историческом
имени `Link_891_403_1` не разбирается. Локальные ID и направления читаются из
`dbo.ParameterGroups.PK`, `MasterGroupID`, `SlaveGroupID` выбранной базы.
Сервер и база дополнительно проверяются при каждом открытии контекста. При несовпадении
с `ExpectedServer`/`ExpectedDatabase` запрос прекращается, другие источники не подставляются.

## Запуск в отдельном тестовом экземпляре

1. Сначала соберите проект: `scripts/Check-ProductStage.ps1`. В нём также есть проверки
   чистых правил C# и, при наличии Node.js, JavaScript. Тесты не обращаются к MSSQL.
2. Оставьте существующие строки соединений. В своей секции `Reporter` добавьте только
   `ProductExplorer` из `Reporter/Product/product-profile.example.json`.
   Пример НЕ загружается автоматически и не заменяет весь `appsettings.json`.
3. Для источника `tdocs` уже должен существовать свежий каталог `app.TflexGroup` и
   `app.TflexRelation`. При необходимости выполните только синхронизацию метаданных.
   Старую кнопку сброса/начальных настроек повторно нажимать не требуется.
4. Выполните `Reporter/sql/008a_product_access_seed.sql` в СОБСТВЕННОЙ БД репортера.
   Скрипт добавляет отсутствующие политики для выбранного источника/роли, существующие
   настройки и отключения не перезаписывает. T-FLEX БД этим скриптом не изменяется.
   В случае ранее отключённых политик разрешите нужные три справочника и четыре связи
   через существующую административную страницу.
5. Запустите отдельный локальный экземпляр с `ASPNETCORE_ENVIRONMENT=Development`.
   Не переключайте действующий промышленный экземпляр в Development ради проверки.
   Новые маршруты в этом этапе намеренно закрыты вне Development даже для администратора.
6. Откройте `/reporter/product.html?source=tdocs&cardId=183`.

Минимальный фрагмент конфигурации:

```json
{
  "Reporter": {
    "ProductExplorer": {
      "Enabled": true,
      "AllowAnonymousInDevelopment": true,
      "Sources": {
        "tdocs": {
          "ExpectedServer": "SRV-TDOCS",
          "ExpectedDatabase": "TFlexDOCsOne",
          "FolderClassIds": [79],
          "FileClassIds": [82, 110],
          "StructureTypeIds": [1, 2, 3, 4, 5, 6, 7, 8, 9],
          "ExcludedProductClassIds": [696, 697]
        }
      }
    }
  }
}
```

По умолчанию `Enabled=false`, разрешённых источников нет, а анонимный вход не разрешён.
`AllowAnonymousInDevelopment` допускает только отдельный тестовый режим в Development;
его нельзя считать промышленной авторизацией. Нынешние `Reporter:SecurityMode` и
`DebugWindowsLogin` не изменяются этим патчем.

Числа классов и видов структуры выше принадлежат ТОЛЬКО профилю `tdocs`. Классы папок
и файлов проверяются по `Classes.GroupID` текущего справочника Files; учитывается
наследование `BaseClassID`. Неизвестный класс показывается как «Тип не подтверждён»,
а не определяется по точке в имени. Профили других серверов автоматически не создаются.

## Данные и права

Новый код читает только заранее описанные таблицы и связи. Значения параметризованы;
имена проходят экранирование и проверку в метаданных. SQL из браузера не принимается.
Направление обхода задаётся парой исходного/целевого справочника, а не совпадением
числа ObjectId с любым концом связи. `Both` в политике означает разрешение пройти
подтверждённую сторону; SQL `MasterID=@id OR SlaveID=@id` не применяется.

Политики `app.GroupAccessPolicy` и разрешение связей проверяются в новом просмотре
всегда, включая Preview. `TflexRead` дополнительно вызывает существующий расчёт прав.
Доступные объекты выбираются в ограниченном окне чтения; при продолжении сохраняется
курсор. Недоступная строка не сериализуется. Кэш решений существует лишь внутри одного
запроса и включает локальный справочник и объект; контекст принадлежит одному источнику.

Это НЕ устраняет известные ограничения старого ACL (наследование прав, усечение правил,
сопоставление пользователей, повторное назначение DefaultRoleCode). Поэтому данный
выпуск не разрешён в Production. Следующий этап должен закрыть WinAuth, RealUser /
EffectiveUser, проверку прав и безопасное скачивание. Тесты предварительного режима
не являются доказательством доступа другого сотрудника.

Новый просмотр не отдаёт физических путей и ссылок на старое скачивание. Его файловая
таблица показывает имена, типы, версии и размер. Старый маршрут интеграции не удалён,
не переименован и не закрыт неожиданно. Его токен/служебная учётка — отдельный шаг.

## Правила сохранённого состава

Для проверяемого режима выбраны актуальные строки с `s_ClientViewID=0`, `s_Deleted=0`,
`s_State=0`. Личный ClientViewID=1431 из профиля не переносится в репортер.
Связи читаются при `DeletedChangelistID=0` и `AddedClientViewID=0`; незавершённое
удаление другой сессией само по себе не считается сохранённым удалением.
Полная работа с персональными черновиками в этом этапе отсутствует.

Состав читается через `NomenclatureHierarchy` с проверкой дат: начало включительно,
конец исключительно. `UsingInStructures` используется через EXISTS, чтобы несколько
подходящих видов структуры не размножали одно вхождение. Стартовый набор видов 1…9
и исключения классов повторяют профиль запроса, а не выводятся из единственной строки
CSV с видом 1. В интерфейсе показывается дата применимости; актуальные данные перечитываются
при запросах, это не транзакционно закреплённый снимок всего пользовательского сеанса.

Поддержан основной состав `s_ProductStructureID=0`, `s_DesignContextId=0`.
Вставленная структура с `s_InsertedStructureID!=0` отмечается и не раскрывается как
обычный состав. Непустой Context в межсправочной связи вызывает диагностическую
остановку вместо угадывания его смысла. Объединение ревизий/контекстов — не часть этого этапа.

Узел дерева определяется полным путём вхождений от корня; объект и вхождение не смешиваются.
Повторный объект в разных ветках не удаляется. Цикл проверяется только внутри текущего пути.
Каждый запрос детей и файлов повторно проверяет путь от карточки и назначенного корня:
подставить чужой parentId, rootId или folderId и получить его данные нельзя.

Количество выводится из `Amount`, а не из `Quantity`. Это проверяемый выбор для текущего
профиля: в CSV Amount=1, Quantity=0. Обобщённая семантика Quantity не утверждается.
Позиция и единица не заполняются выдуманными значениями при NULL/пустой строке.
Сортировка страниц пока технически стабильная (ID строки/вхождения), не точная штатная
сортировка спецификации. В следующем аудите проверить порядок на реальной сборке.

## Новые маршруты

Базовый префикс — `/api/reporter/product`.

```text
GET /sources
GET /sources/{sourceCode}/cards?query=...&after=0
GET /sources/{sourceCode}/cards/{cardId}/roots
GET /sources/{sourceCode}/cards/{cardId}/roots/{rootId}/children?path=...&asOf=...&after=0
GET /sources/{sourceCode}/cards/{cardId}/roots/{rootId}/file-roots?category=pdf&path=...&asOf=...
GET /sources/{sourceCode}/cards/{cardId}/roots/{rootId}/files?category=pdf&path=...&folderPath=...&asOf=...&after=0
```

`path` — последовательность s_HierarchyLinkID от назначенного корня, не s_ObjectID.
`folderPath` — путь от папки, действительно назначенной выбранному изделию, включая корень.
Пользователь эти значения вручную не вводит: ими управляет дерево.
`NextCursor` передаётся следующему запросу как `after`. Пустая страница с `HasMore=true`
допускает продолжение чтения после проверки недоступных объектов; общий размер скрытых
данных не возвращается. Глубина, размер страницы и бюджет ограничиваются сервером.

## Приёмка на подтверждённом примере

- Источник: `tdocs / SRV-TDOCS / TFlexDOCsOne`.
- Карточка 183 → назначенное изделие 23900: `КТ.1204113.39 — Изделие`.
- Первый уровень: вхождение 272674, объект 23904,
  `КТ.1204113.39.00 — Компенсатор тканевый`, Amount=1.
- PDF: папка 101426, файлы 101436 и 101437.
- CAD: папка 101425, файлы 101434 (версия 2) и 101435 (версия 1).
- DXF: папка 101427 назначена; в переданном срезе детей нет.

Эти ID используются только для ручной приёмки и документации, не как константы runtime.
Подробные данные более глубокого состава и файлы дочернего элемента в переданном
срезе не подтверждены. Их проверить при раскрытии. Отсутствие собственной папки у
выбранной детали не компенсируется незаметной подстановкой файлов корня.

Перед промышленным выпуском дополнительно проверить: отказы прав на пути, повторные
вхождения, циклы, контекстные/вставленные структуры, изменения состава между запросами,
пагинацию больших наборов и остальные источники. Строгие проверки прав могут быть
дорогими: пока используется существующий построчный evaluator, не batch-ACL.

## Сборка и откат

Версии NuGet и TargetFramework не менялись. В DocsApi.csproj добавлено исключение
`tests/**/*.cs`, чтобы консольные проверки не попадали в веб-приложение.

```powershell
.\scripts\Check-ProductStage.ps1
```

Команда dotnet build собирает проект и зависимости; это отдельная проверка, не заменяемая
проверкой синтаксиса JS. Документация: https://learn.microsoft.com/en-us/dotnet/core/tools/dotnet-build

Быстро отключить новый этап: `Reporter:ProductExplorer:Enabled=false` и перезапустить
тестовый экземпляр. Схему БД мигрировать назад не требуется. Созданные отсутствовавшие
политики при необходимости отключаются в БД/админке репортера. Старые политики не сбрасываются.
