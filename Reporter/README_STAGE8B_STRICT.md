# Этап 8.1Б.1 — Windows-вход, строгие решения, журнал

Основа: `1981018b25fe193953f9968c67917940db39f1d2`.
Git tree проверен: `ef789cf25d25f2d20e679df1d4c7289695d758b6`.
Это отдельный проверяемый этап безопасности, **не готовый полный промышленный выпуск**.

## Сначала прочитать

1. Новая сборка всегда работает строго. `Preview`, тестовые логины, `[AllowAnonymous]` старого контроллера не открывают доступ.
2. Неподтверждённое решение означает `Allowed=false`. В журнале сохраняется различие между `Denied` и `Indeterminate`.
3. Не заявляется полное равенство штатному ACL DOCs. В частности, не реализованы специальные субъекты, общие назначения, авторы, этапы, связи и обязательный доступ. Они **не игнорируются ради положительного разрешения**.
4. Значение `CommandID=1` не признано автоматически командой чтения. Справочник без подтверждённого системного профиля чтения получает `read_profile_unverified`.
5. Даже после подтверждения номера команды неизвестное общее правило блокирует затронутый справочник. На анонимизированном срезе из 27 случаев новая модель не выдаёт ни одного разрешения. Это не означает запрет всех этих действий в DOCs: это более узкое поведение репортера при неполном знании правил.
6. **Старые API, включая `/api/files/objectid`, в этой сборке закрыты (410 для вошедшего пользователя).** Внешнюю интеграцию не переключать на эту сборку. Проверять в отдельном экземпляре/порту IIS, оставив действующую интеграцию на прежнем экземпляре. Миграция скачивания и служебной учётки/токена — следующий отдельный пакет. Нельзя вернуть anonymous-route как обход.
7. Не добавлены: объединение всех серверов в стартовом окне, дерево направлений, скачивание, «проверить как другой пользователь», новый UI администрирования. Это не скрытые обещания готовности. Сохранён просмотр изделия; убраны его старые разработческие предупреждения и ссылка на старую страницу.

## Что изменено

- Обязательный Negotiate/Windows-вход, включая HTML, CSS и JS рабочего экрана.
- Отдельная проверка Windows SID; чужие `login`, `userId`, `SID` из URL/заголовка не принимаются.
- SID-first сопоставление DOCs, отказ при неоднозначности и несовпадении SID. Короткий логин допустим только при явном разрешении и доверенном домене, и только если у единственной строки DOCs не заполнен SID.
- Членство раскрывается со всех ветвей, включая непервичные. Проверяются лимиты, дубли текущих записей, циклы и необычные интервалы членства. Кэш только в пределах HTTP-запроса.
- Сервер и БД сверяются с профилем; справочник берётся из его локального `ParameterGroups.PK`.
- Данные области доступа берутся из `s_AccessObjectID`, а не автоматически из `s_ParentID`. Нулевая/неподтверждённая область, многоступенчатая цепочка области, этап/мандатный уровень — отказ.
- Правило известного поддержанного вида требует явного назначения на объект/область и явной команды подтверждённого профиля. Caption группы никогда не участвует в разрешении. При конфликте положительного и отрицательного командного состояния применяется консервативный запрет репортера (не объявляется штатным приоритетом DOCs).
- Проверка неготового справочника выполняется до поиска его объектов. Ошибка проверки не маскируется под пустой справочник.
- `AppUser.IsEnabled` соблюдается. Стартовая роль `ProjectCardViewer` назначается только при первом создании пользователя. Отозванная роль больше не возвращается при следующем запросе. Автоматического назначения администратора нет.
- Политики публикации принимаются только с конкретным `SourceId`. Старые глобальные строки `SourceId=NULL`, завязанные на локальный ID, не расширяют выдачу.
- Старая эвристика оставлена в исходниках для истории, но исключена из DI. Старые контроллеры не находятся в списке публично разрешённых обработчиков.

## Развёртывание отдельного проверочного экземпляра

### 1. Сборка

Из корня проекта:

```powershell
.\scripts\Check-StrictStage.ps1
```

Пакеты NuGet и TargetFramework исходного проекта не обновлялись.

### 2. Журнал в собственной БД

Отдельно сохранить резервную копию настроек/БД репортера. Выполнить `Reporter/sql/008b_strict_audit.sql` **в БД приложения**, не в `TFlexDOCsOne`, `TFlexDOCsPKB` или другой БД DOCs.

Миграция создаёт `app.ReporterSecuritySchema` и `app.ReporterAuditEvent`. Не изменяет права DOCs, пользователей DOCs и политики публикации. Не очищает существующий журнал.

Runtime также проверяет AppConnectionString перед записью: системные БД и база с `dbo.ParameterGroups` не принимаются. Подключения к DOCs должны использовать отдельно выданные SELECT-права; ApplicationIntent и название фабрики сами по себе не делают SQL-учётку read-only.

Служебной учётке репортера нужны SELECT/INSERT/UPDATE на его служебных таблицах в своей БД. Для данных DOCs — только чтение. Миграции выполняет администратор отдельно, DDL из приложения нет.

### 3. Настройки

Слить `Reporter/StrictAccess/strict-runtime.example.json` со своей конфигурацией, **не заменяя** AppConnectionString, SourceConnectionStrings и имеющиеся ProductExplorer.Sources.

Обязательные изменения старой конфигурации:

```json
"DebugWindowsLogin": null,
"DebugWindowsSid": null,
"ProductExplorer": { "AllowAnonymousInDevelopment": false }
```

Старая настройка SecurityMode больше не отключает новый механизм. При оставленных отладочных идентификаторах или анонимном флаге приложение останавливается при запуске.

`AdministratorSids`: реальные Windows SID сотрудников, которым разрешён просмотр системного журнала и проверки **своей** учётной записи. Пустой список означает отсутствие доступа к этим техническим маршрутам. Посмотреть свой SID можно командой `whoami /user`. Администратор не получает обхода DOCs ACL.

`VerifiedObjectReadCommands`: служебное сопоставление `sourceCode → ParameterGroups.Guid → номер подтверждённой команды чтения объектов`. По умолчанию **пустое**. Это не роли и не таблица «человек → направление».

Не вписывать `1` только ради исчезновения отказа. В этой итерации смысл команды не объявлен доказанным. Поддержка каждого неподтверждённого режима может добавляться отдельно после ручной сверки. Нельзя выключать строгий режим ради сверки; диагностические причины остаются в журнале.

Пример формы (НЕ готовая настройка):

```text
VerifiedObjectReadCommands
  <проверенный источник>
    <GUID локального определения справочника>: <подтверждённый номер команды>
```

Первоначальный профиль `tdocs` и его классы не копировать на PKB автоматически. Не заданный/ошибочный профиль источника отказывает в выдаче.

Если старые публикации имеют SourceId=NULL, воспользоваться существующим `008a_product_access_seed.sql` для выбранного источника после проверки метаданных. Он добавляет отсутствующие source-specific строки и не должен использоваться для изменения доступа DOCs.

### 4. IIS / Windows Authentication

В отдельном приложении IIS включить Windows Authentication, отключить Anonymous Authentication, использовать HTTPS и действующий Hosting Bundle для целевой платформы. Проверить автоматический вход браузера в корпоративном домене.

Порядок middleware: HTTPS → routing → authentication → строгий периметр → authorization → static files → controllers. Старые AllowAnonymous не обходят периметр. Не включать Swagger перед ним.

При Kestrel также используется зарегистрированный Negotiate. Прокси не должен подменять пользователя произвольным HTTP-заголовком. Делегирование Windows-токена к SQL не используется: SQL-учётка служебная, прикладная проверка выполняется отдельно.

Отказы, завершённые самим IIS до ASP.NET (например, начальный 401), не могут появиться в SQL-журнале приложения: сохраняйте также IIS-журнал.

### 5. Проверки

- Открыть `/reporter/product.html` и `/api/reporter/strict/me` без отладочного логина: подтверждается текущий Windows-пользователь.
- Неавторизованный запрос: challenge/401; при проблеме журнала возможен 503, но данных нет.
- Источник и роль публикации должны быть настроены как раньше, с конкретным SourceId.
- Найти карточку: если имеется неизвестное общее правило или нет профиля чтения, ожидается 403 «Не удалось подтвердить право просмотра», а не выдача и не ложное сообщение об отсутствии данных.
- Проверить `app.ReporterAuditEvent`: StartedUtc, ActorLogin, Operation, ResourceJson, Phase, DecisionsJson.
- Удалить роль тестового пользователя в своей БД репортера: следующий запрос не должен вернуть роль.
- Отключить AppUser: доступ запрещён. Назначения в DOCs не меняются.
- Проверить старые `/api/reporter/security/...`, `/reporter/admin.html`, `/api/files/objectid`: они не должны раскрывать данные в этой сборке.
- Остановить доступ к журналу: успешная выдача не допускается.

Системные маршруты (только AdministratorSids, кроме me):

```http
GET /api/reporter/strict/me
GET /api/reporter/strict/sources/{sourceCode}/references/{referenceId}/objects/{objectId}/decision
GET /api/reporter/strict/audit?after=0&take=100
```

Политики/матрицы сотрудников этим API не редактируются. Режим «под другим сотрудником» не реализован; переданные соответствия служат только проверочными данными.

## Журнал: что считается событием

`Product.Search` — запрос поиска; `Product.Roots` — получение карточки и корня; `Product.Children` — получение уровня состава; `Product.FileRoots` — назначенные папки; `Product.Files` — получение списка файлов. `System.*` — системные запросы. `Route.Refused` — попытка старого/неразрешённого маршрута.

Запись `Started` сохраняется до действия. `ReadyToReturn` с решениями сохраняется до сериализации ответа. При ошибке этой записи данные не выдаются. `Completed` означает завершение серверного обработчика, а не доказанное прочтение человеком. Отдельное скачивание пока не реализовано и не имитируется статистикой просмотров списка.

При падении процесса может остаться Started/ReadyToReturn; это незавершённое событие, не успешный просмотр. Ошибка финального обновления после начала ответа журналируется как AUDIT_UNAVAILABLE/AUDIT_COMPLETION_FAILED, соединение прерывается; уже отправленные байты нельзя «отозвать». Журнал не является криптографически неизменяемым: ограничить права SQL, защитить резервные копии и назначить регламент хранения.

Не записываются Authorization, пароли, токены, произвольная QueryString, содержимое файлов. Имена пользователя, SID и идентификаторы ресурсов нужны для аудита; доступ к SQL-журналу должен быть ограничен.

## Проверки и ограничения поставки

В окружении подготовки отсутствует .NET SDK и доступ к вашей MSSQL/домену. `dotnet build`, C#-проверки, WinAuth/IIS, миграция и HTTP-интеграционные проверки здесь **не запускались**. Не трактовать файл как пакет с успешно пройденной сборкой.

Выполнены: проверка исходного Git tree, JS syntax, 12 существующих Node-тестов, 20 Python-проверок офлайн-модели/инвариантов (включают 27 анонимизированных регрессий). Python-модель не является исполнением C#. Отдельный C# console-проект содержит те же регрессии и дополнительные чистые проверки; запускается Check-StrictStage.ps1 на вашей стороне.

Фикстуры обезличены: в них нет ФИО, логинов, реальных названий серверов и исходных GUID. Производственные CSV не включены.

## Следующие самостоятельные шаги

1. Совместимый защищённый маршрут скачивания и отдельная учётная запись интеграции/ограниченный токен, события начала/завершения/прерывания передачи. До этого прежняя интеграция остаётся на прежнем экземпляре.
2. Все источники автоматически, общая левая панель направлений, группировка после проверки каждой серверной привязки. Сейчас выбор источника ещё сохранён.
3. Последовательная поддержка подтверждённых режимов ACL без возврата к разрешениям по именам, UserID=0 или неизвестному числовому флагу.
